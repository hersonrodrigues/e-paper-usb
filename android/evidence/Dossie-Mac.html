OBJETIVO
Criar um aplicativo Android para selecionar uma foto e enviá-la diretamente
à tela e-paper pelo cabo, substituindo o ImageToUSB do Windows.
O Mac será usado para desenvolver e compilar o APK; o aplicativo rodará
no celular Android. O driver SETUP.EXE não deve ser instalado no Mac.

ESTADO REAL DA ENTREGA
Este pacote é um dossiê de engenharia e uma base de protocolo Java.
Ainda NÃO é um projeto Android completo, nem um APK. Faltam interface,
integração USB, processamento da imagem, tratamento de conexão e build.
A análise foi estática, com leitura do registro do Windows e do log da
janela do ImageToUSB. Não houve captura USB nem teste da reprodução.
A execução de javac no Windows retornou Access is denied; nenhum teste
Java foi executado. Não interpretar os testes incluídos como aprovação.

PEDIDO PRONTO PARA COLAR NO ASSISTENTE DO MAC

Crie um projeto Android completo e gere um APK de debug para enviar fotos
de um celular Android por USB OTG a uma tela e-paper Good Display 800x480
de quatro cores. Use os arquivos deste dossiê como evidência técnica.
Não confunda com copiar arquivos por MTP, Wi-Fi ou rodar EXE no Android.

Use a biblioteca usb-serial-for-android, com suporte CH34x. Consulte o
README oficial e fixe uma versão publicada. Detecte VID=0x1A86/PID=0x7523.
Declare android.hardware.usb.host. Solicite a permissão USB via UsbManager
e trate recusa, reconexão, desconexão, concorrência e liberação da porta.
Não envie automaticamente ao conectar: o usuário deve tocar em Enviar.

Crie interface em português com seleção de foto pelo seletor do sistema,
prévia, ajuste proporcional para 800x480 (cortar ou preencher), rotação,
conversão para preto/branco/amarelo/vermelho e opção de dithering.
Normalize orientação EXIF, componha transparência sobre fundo branco e
limite a decodificação de imagens grandes para evitar falta de memória.
Prévia e bytes enviados devem representar a mesma imagem final.

Execute o trabalho de USB fora da thread da interface. Configure 115200,
8N1, RTS=true e DTR=false. Envie o cabeçalho de 12 bytes descrito no
Protocolo-USB.txt e aguarde um ACK completo e válido de 10 bytes com F1.
Leituras podem vir fragmentadas ou concatenadas: implemente um parser
com buffer, sincronização A0 50, checksum e timeout limitado. Não envie
pixels após timeout ou resposta inválida. Não invente bytes de resposta.

O comprimento no cabeçalho é 48000 (BB 80), mas o payload de quatro cores
tem 96000 bytes. Modelo C4. Cada byte empacota quatro pixels, MSB primeiro.
Envie 23 blocos de 4096 e um de 1792, cada um seguido de 0D 0A; faça pausa
de 100 ms após cada bloco completo. Não trate 0D 0A como CRC calculado.
Use o código Java incluído ou porte-o preservando os testes conhecidos.

Use timeout de escrita suficiente para o bloco inteiro; trate falhas e
cancelamento sem repetir automaticamente uma transmissão parcial.
Se uma transmissão ficar incompleta, encerre a sessão e oriente reiniciar
o dispositivo antes de tentar novamente; não invente comando de abortar.
Não chame DiscardOutBuffer após o envio. Não anuncie atualização física
concluída sem evidência: o log do original apenas registra o fim do envio.
Permita exportar localmente um log de diagnóstico (TX/RX do cabeçalho,
ACK, tamanho de blocos, tempos e erros), sem envio de dados à internet.

Valide checksum, códigos de cor, tamanho, blocos, ACK fragmentado, timeout,
desconexão e preservação da prévia. Gere README com build no macOS e teste
físico. Separe claramente compilação, testes offline e teste no hardware.
Entregue o APK, fonte completo e resultado real dos testes, sem afirmar
que a comunicação física foi validada antes de testar o painel.

Protocolo-USB.txt

ANÁLISE DO IMAGETOUSB v4.0 — 30/09/2026

RESULTADO
O envio usa uma porta serial por USB (CH340). O programa converte pixels
em um fluxo próprio para a tela e-paper; não copia um JPG para uma pasta.
Esta análise cobre o caminho 800 x 480 em quatro cores.

EVIDÊNCIAS LOCAIS
- Registro do Windows: USB-SERIAL CH340 (COM3), serviço CH341SER_A64,
  identificador USB VID_1A86 / PID_7523.
- Janela do ImageToUSB: COM3, 4-Color, 7.5 Inch, Resolution:800x480,
  Successful handshake, Data complete:100%, E-Paper Datas=96000.
- Duas janelas do ImageToUSB estavam abertas. Uma continha o histórico
  de envio; a outra, apenas a mensagem de conexão.
- SETUP.EXE contém referências a CH341SER.INF e drivers CH341.
- ImageToUSB é um executável .NET. Suas instruções IL foram lidas com
  ReflectionOnlyLoadFrom/GetMethodBody, sem executar métodos do programa.
- Não foi realizada captura ao vivo dos pacotes USB, nem recuperado o
  tráfego de uma transferência passada. Nenhum novo envio foi disparado.

CONFIGURAÇÃO SERIAL
SetPortProperty: baud=115200; RTS=true; ReadTimeout=-1.
Demais parâmetros não são alterados nessa rotina: valores padrão da
SerialPort (.NET), ou seja, 8 bits, sem paridade, 1 stop bit, sem handshake
automático e DTR=false. Verificar no teste físico a configuração Android.

NEGOCIAÇÃO INICIAL (Shake_hands_data)
O botão Display envia 12 bytes:
AA 55 E1 BB 80 04 C4 RR SS FF 0D 0A

AA 55: prefixo.
E1: comando inicial.
BB 80: 48000 em big-endian = 800*480/8. Atenção: este campo NÃO é
       96000, mesmo no modo de quatro cores.
04: quatro cores.
C4: identificador selecionado pelo programa para 800x480.
RR: 01 quando a rotina de detecção encontra vermelho; caso contrário 00.
SS: soma dos bytes 0..7, módulo 256. É E3 com RR=00; E4 com RR=01.
FF 0D 0A: final do cabeçalho.

O teste de vermelho usado pelo programa é R>100, G<=100 e B<=100.
O estado interno desse indicador pode depender de imagens anteriores;
a implementação nova calcula o indicador para a imagem atual.

RESPOSTA ESPERADA (sp_DataReceived e callback)
10 bytes, começando por A0 50, comando F1 no byte 2, soma dos bytes
0..7 no byte 8 e FF no byte 9. Os campos 3..7 não são interpretados
no caminho de envio identificado. Depois desse ACK, Picture_data_send
é chamado. Não se deve enviar pixels sem receber/validar o ACK.

Há também uma rotina SerialDataAnalysis que menciona F2, mas o callback
de recepção que inicia o envio usa F1. Não confundir os dois caminhos.
A implementação nova deve juntar leituras parciais e impor timeout;
o original faz uma leitura de até 10 bytes e não valida o tamanho lido.

FORMATO DOS PIXELS (GetPictureData_4Color)
Para 800x480: linhas de cima para baixo, pixels da esquerda para direita.
Quatro pixels por byte, primeiro pixel nos bits 7..6, depois 5..4, 3..2,
1..0. São 800*480/4 = 96000 bytes.

Código de pixel:
00: preto (R,G,B <= 50).
01: branco (R,G,B >= 200).
11: outros pixels cuja média inteira (R+G+B)/3 <=127; inclui vermelho puro.
10: demais pixels; inclui amarelo puro.

Exemplo: preto, branco, amarelo, vermelho -> 00 01 10 11 -> byte 1B.
Tons de cinza intermediários também viram 10/11 nessa função; para fotos,
preparar antes uma paleta de quatro cores, opcionalmente com dithering.
As cores físicas dos códigos 10/11 ainda devem ser conferidas no painel.

BLOCOS DE ENVIO (Picture_data_send)
23 blocos com 4096 bytes de pixels cada + um último de 1792 bytes.
Depois de CADA bloco, o programa envia 0D 0A. A variável chamada data_CRC
contém apenas esses dois bytes: não é um CRC calculado sobre os pixels.
O original espera 100 ms após cada bloco completo.
Não há espera por ACK de cada bloco nesse caminho do programa.
Total de pixels + separadores = 96048 bytes; com cabeçalho = 96060 bytes.
Esses blocos são do protocolo da aplicação, não os pacotes físicos USB.

O original exibe E-papaer update... ao terminar as chamadas de escrita;
isso não é uma confirmação de que o painel concluiu a atualização.
Também chama DiscardOutBuffer ao final: uma nova implementação deve
garantir o término efetivo das escritas, sem descartar bytes pendentes.

PARA UM APLICATIVO ANDROID
O celular deve atuar como USB host/OTG e reconhecer o CH340. Usar um
driver Android CH34x, pedir permissão USB pelo sistema e configurar a
porta serial. SETUP.EXE é um instalador Windows, não um driver Android.
Sequência: escolher foto -> ajustar para 800x480 -> converter cores ->
conectar USB -> enviar cabeçalho -> validar ACK -> enviar blocos ->
aguardar a atualização física do painel.

EpaperProtocol.java fornece o empacotamento e a validação, sem dependência
de Android ou de driver e sem abrir portas. Não é um APK ou aplicativo
completo. Os testes fornecidos são offline e ainda não foram executados; não validam hardware.

EpaperProtocol.java

import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;

/** Protocol reconstructed statically from the supplied ImageToUSB v4.0.
 * Scope: 800x480, four colors. NOT yet verified with a live device.
 * No USB operations are performed by this class.
 */
public final class EpaperProtocol {
    public static final int WIDTH = 800, HEIGHT = 480;
    public static final int BAUD_RATE = 115200, BLOCK_SIZE = 4096;
    public static final int VENDOR_ID = 0x1A86, PRODUCT_ID = 0x7523;
    private EpaperProtocol() {}

    // Matches GetPictureData_4Color, including its coarse RGB thresholds.
    // For photographs, quantize/dither to the display palette BEFORE this step.
    public static int pixelCode(int rgb) {
        int r = (rgb >>> 16) & 255, g = (rgb >>> 8) & 255, b = rgb & 255;
        if (r <= 50 && g <= 50 && b <= 50) return 0;
        if (r >= 200 && g >= 200 && b >= 200) return 1;
        return ((r + g + b) / 3 <= 127) ? 3 : 2;
    }

    /** Opaque RGB pixels, row-major, exactly 800x480. Alpha is ignored. */
    public static byte[] pack(int[] rgb) {
        if (rgb == null || rgb.length != WIDTH * HEIGHT)
            throw new IllegalArgumentException("Expected 800x480 pixels");
        byte[] out = new byte[WIDTH * HEIGHT / 4];
        for (int i = 0; i < rgb.length; i += 4) {
            out[i / 4] = (byte) ((pixelCode(rgb[i]) << 6)
                | (pixelCode(rgb[i+1]) << 4)
                | (pixelCode(rgb[i+2]) << 2) | pixelCode(rgb[i+3]));
        }
        return out;
    }

    public static boolean containsRed(int[] rgb) {
        if (rgb == null || rgb.length != WIDTH * HEIGHT)
            throw new IllegalArgumentException("Expected 800x480 pixels");
        for (int pixel : rgb) {
            if (((pixel >>> 16) & 255) > 100 && ((pixel >>> 8) & 255) <= 100
                && (pixel & 255) <= 100) return true;
        }
        return false;
    }

    /** The length field is the ONE-bit plane size (48000), even for 4 colors. */
    public static byte[] handshake(boolean redPresent) {
        byte[] frame = {(byte)0xAA, 0x55, (byte)0xE1, (byte)0xBB, (byte)0x80,
            4, (byte)0xC4, (byte)(redPresent ? 1 : 0), 0, (byte)0xFF, 13, 10};
        int sum = 0;
        for (int i = 0; i < 8; i++) sum += frame[i] & 255;
        frame[8] = (byte)sum;
        return frame;
    }

    /** Reassemble a full 10-byte frame before calling: serial reads may split it. */
    public static boolean isHandshakeAck(byte[] frame) {
        if (frame == null || frame.length != 10 || (frame[0] & 255) != 0xA0
            || (frame[1] & 255) != 0x50 || (frame[2] & 255) != 0xF1
            || (frame[9] & 255) != 0xFF) return false;
        int sum = 0;
        for (int i = 0; i < 8; i++) sum += frame[i] & 255;
        return (sum & 255) == (frame[8] & 255);
    }

    /** Send only AFTER a valid handshake response. Each packet includes CR LF.
     * Match the original 100 ms pause after each full block; handle write errors.
     * These are application blocks, not physical USB packet boundaries.
     */
    public static List<byte[]> packets(byte[] pixels) {
        if (pixels == null || pixels.length != 96000)
            throw new IllegalArgumentException("Expected 96000 bytes");
        List<byte[]> out = new ArrayList<>();
        for (int offset = 0; offset < pixels.length; offset += BLOCK_SIZE) {
            int count = Math.min(BLOCK_SIZE, pixels.length - offset);
            byte[] packet = Arrays.copyOfRange(pixels, offset, offset + count + 2);
            packet[count] = 13;
            packet[count + 1] = 10;
            out.add(packet);
        }
        return out;
    }
}

TestEpaperProtocol.java

import java.util.Arrays;
import java.util.List;
public class TestEpaperProtocol {
    static void require(boolean value, String message) {
        if (!value) throw new AssertionError(message);
    }
    public static void main(String[] args) {
        byte[] expected = {(byte)0xAA,0x55,(byte)0xE1,(byte)0xBB,(byte)0x80,4,
            (byte)0xC4,0,(byte)0xE3,(byte)0xFF,13,10};
        require(Arrays.equals(expected, EpaperProtocol.handshake(false)), "handshake");
        require((EpaperProtocol.handshake(true)[8] & 255) == 0xE4, "red checksum");
        int[] rgb = new int[800*480];
        for(int i=0; i<rgb.length; i+=4) {
            rgb[i]=0; rgb[i+1]=0xffffff; rgb[i+2]=0xffff00; rgb[i+3]=0xff0000;
        }
        byte[] packed = EpaperProtocol.pack(rgb);
        require(packed.length == 96000, "payload size");
        for(byte b: packed) require(b==0x1b, "pixel order or color mapping");
        require(EpaperProtocol.containsRed(rgb), "red flag");
        List<byte[]> packets=EpaperProtocol.packets(packed);
        require(packets.size()==24 && packets.get(23).length==1794, "packet count/tail");
        int offset=0, total=0;
        for(byte[] p: packets) {
            require(p[p.length-2]==13 && p[p.length-1]==10, "terminator");
            for(int i=0;i<p.length-2;i++) require(p[i]==packed[offset++], "payload intact");
            total+=p.length;
        }
        require(offset==96000 && total==96048, "wire data size");
        byte[] ack={(byte)0xA0,0x50,(byte)0xF1,0,0,0,0,0,(byte)0xE1,(byte)0xFF};
        require(EpaperProtocol.isHandshakeAck(ack), "valid synthetic ACK");
        ack[8]=0;
        require(!EpaperProtocol.isHandshakeAck(ack), "bad checksum rejected");
        require(!EpaperProtocol.isHandshakeAck(new byte[3]), "partial ACK rejected");
        System.out.println("PASS: handshake, RGB packing, red flag, 24 blocks, payload preservation, ACK validation. No device accessed.");
    }
}
